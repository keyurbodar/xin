# 17–18 · Failures and cost

This section decides where each failure is caught and what the user sees, and records the DO row-cost model that Xin accepts at personal scale.

Read with: [01 Host](./01-host.md) for the alarm and Harness recovery paths, [03 Commands and wire](./03-commands-and-wire.md) for receipts, [04 Intake and dispatch](./04-intake-and-dispatch.md) for claim and submit recovery, [06 Orchestration](./06-orchestration.md) for the watchdog.

## 17 · Failure matrix

| Failure | Where it's caught | User sees |
| --- | --- | --- |
| Same command sent twice (reconnect) | `receipts`, or the intake item's `commandId` for `message.send` | one message |
| Crash between claim and submit | boot scan: claimed rows without a submission are resubmitted with the same requestId | nothing |
| Eviction mid-stream | pi failed attempt → retry, resumed by the run's own next step | partial text resets, then completes |
| Eviction mid-tool | `replay:"safe"` tools re-run, others get an `interrupted` result, and the model adapts | the tool shows as interrupted, then retried |
| Hung tool or provider | watchdog, 2 min | "stopped: no progress…" report |
| Provider down | pi retry → run unanswered → report or error bubble | error names the provider and offers a model switch |
| Storage error | `harness.closed` → `ctx.abort()` → fresh instance | socket reconnects, snapshot |
| Alarm write fails | `ctx.abort()`, so the constructor's fallback alarm re-arms | nothing |
| Plugin throws | a throwing tool gives an error result, a throwing hook is reported and skipped, a row that fails to start is marked `failed` with its error and its effects unwound; other rows keep running, and a failed required row puts Home in `boot_failed` | the plugin shows as failed in settings |
| Deploy changes a plugin's tool | running calls finish on the old code and the next phase uses the new (pi reload rule) | nothing |

## 18 · Cost model (DO SQLite rows written, about $1 per million)

| Event | Rows written (approx.; reads and statements where noted) |
| --- | --- |
| Burst intake (3 messages) | 3 enqueue commits + 1 claim + 1 done, one journal row each, and no receipt row |
| Coordinator reply, no tools | user entry + assistant entry + live/inbox docs, all inside the turn's one journal row; pi commits a partial answer at most every `partialIntervalMs` (100 ms by default) and storage gets it with the next commit that reads `pi.live`, at the latest after `persistWithinMs` (1 s) |
| Thread, 20 tool steps | not measured separately: a turn's commits, tool calls and beats included, land in one journal row at the turn's end, so a 20-step turn costs about the 16 below rather than 3 a step |
| One owner message → one reply (`src/cost.test.ts`) | 13 written (bound 18), 15 read (bound 22) |
| One delegate → thread → report → coordinator reply (`src/cost.test.ts`) | 27 written (bound 36), 31 read (bound 46) |
| One message in a 100-thread home, half with two tool calls (`test/load.bench.ts`) | 16 written, 21 read, 49 statements |
| One cold message after eviction, in that home | 11 written, 14 read, 42 statements, after a cold boot that reads 281 rows: 254 replayed journal rows and 27 others |
| One idle alarm in that home | 2 written, 4 read, 12 statements |
| Idle hour | 0 (no alarm armed) |

Both scenario measurements come from the storage meter (`test/meter.ts`) around the real `Home` DO, which counts the rows Cloudflare bills: each cursor's `rowsRead`/`rowsWritten`, each key-value method and each alarm method. The bounds above sit roughly a third to a half over the measurements (18 against 13, 22 against 15, 36 against 27, 46 against 31), so a regression that adds bookkeeping rows fails the test instead of hiding in the average.

**The 100-thread load.** `test/load.bench.ts` (`XIN_LOAD=1 bun scripts/gate.ts run test`) builds one project with 100 thread conversations, sends each thread three messages (half of them two tool calls), fills the journal towards a full checkpoint and evicts once, then fires five idle alarms. `test/meter.ts` wraps the Home's storage and counts what Cloudflare bills: SQL rows from each cursor's own `rowsRead`/`rowsWritten` (its documented billing counters), each key-value method as one row, and each alarm method as one row. The benchmark reports the fireAt move separately from the message, the alarm window as harness rows, and the cold boot replay apart from the turn that follows it; it bounds all of them, so a harness or replay regression cannot hide inside a total.

**pi's state is a journal, not a table per record.** The harness runs on pi's `MemoryStorage`, so its reads are map lookups and a commit reaches disk as one journal row holding that commit's `StorageWrite`s (`src/kernel/journal.ts`). A flush happens at the commit that settles a submission — the end of a turn — so a two-tool message that runs three model rounds and several tool tasks is still one row. Two other things flush: a commit that changes any document other than `pi.live` (configuration: a model, a thread, a schedule, a project), and a turn that reaches `FLUSH_BYTES` (1 MB) of pending writes. A `pi.live` progress commit is the streamed answer and waits for the turn's boundary, so a long reply does not write one row per second.

A journal alone replays forever, so every `CHECKPOINT_ROWS` (256) journal rows the storage writes the whole state as one commit of `StorageWrite`s — conversations, tasks, submissions, documents, entries — stores it in `pi_checkpoint`, and deletes the journal rows it covers. The rewrite is one transaction, so a crash cannot leave neither the old checkpoint nor the new one, and a replay only reads journal rows newer than the checkpoint's sequence, so a crash before the journal delete does not repeat a commit. A commit waits for a checkpoint in flight before it applies, so the snapshot and the sequence stored with it are the same point in the journal; a journal row whose commits the checkpoint already covers is skipped on replay rather than replayed into a duplicate. A cold start reads that checkpoint and at most 256 journal rows: the 100-thread load's cold boot reads 281 rows, of which 254 are replayed journal rows and the other 27 are the checkpoint's parts, key-value reads and the migration check. Truncation costs one row per row deleted, so the journal's total is about 13.6 rows a message: the 6.7 rows its commits store, the 6.8 rows truncation deletes, and the checkpoint parts the two amortize.

A home that cannot read its journal or checkpoint answers no route but `POST /v1/repair`, which reports the failure and drops the journal rows (`{drop:"journal"}`, the state since the last checkpoint) or the checkpoint too (`{drop:"all"}`) before opening again. It is the escape hatch for a boot that a deploy cannot fix, and it refuses to touch a home that is open. It is reached with the deploy token (`OWNER_TOKEN`), because a home that cannot boot cannot check a rotated session token.

The alarm is the small part of a message: the arm at the start of a fire, the `fireAt` move and the end-of-turn wake find the deadline where it already is and write about 0.4 alarm rows a message between them, because every event that finds an alarm inside the 60 s horizon writes nothing. The four alarm rows a message the benchmark reports separately belong to its own plumbing — it moves `xin.intake`'s `fireAt` by hand to fire the queue — not to the message.

**What that costs in durability.** Writes are durable at a flush, not at a commit. An eviction during a turn loses that turn's unflushed commits; the harness retries the attempt it was in and the client's retry carries the same request id, so the turn runs again rather than being lost — but it can run again, tool calls included, and any tokens it spent are spent twice. Configuration and a finished turn are durable at once. The state also lives in the object's memory, so a home's whole history has to fit in the 128 MB an object gets; the checkpoint is the recovery path, not an off-heap store.

**Where the 16 rows go.** Measured over the 100-thread load, one message is 16.0 rows: the journal 13.6, the batch ledger's two `kv` rows, and about 0.4 of alarm. The journal is nearly all of it — 6.7 rows stored, one per flush, and 6.8 rows the truncation deletes when the journal checkpoints every 256 rows, plus 0.1 of checkpoint parts. A flush is one row however many commits it holds, which is why the tool rounds inside a turn cost nothing extra; the enqueue, the claim, the persist and the done each change a document and so flush on their own. The intake queue being a document rather than a table is what keeps that at one row a flush instead of a row plus an index entry; the command receipt is gone for `message.send`, because its item answers a resend. Everything pi writes is inside the journal row. The hottest reads are point lookups: kv by key, the journal by sequence, and the intake document's snapshot, which is a memory read; the only scan left is the hourly receipt sweep, which is bounded by the index on its age.

A heavy day (300 messages, 40 threads) writes about 5k rows — 4,800 at the measured 16 a message — under 1¢ on the paid plan and 4.8% of a free-plan day's 100,000 rows written. That is why Xin drops kiko's row-budget machinery: a budget mechanism would police a number the agent's own commits set, and at personal scale the meter that still matters most is LLM tokens. The levers are batching (§5), brief-only children (§8), stable sections first (persona → profile → project instructions → skills index), live state as entries and never as changing sections, and the per-message overhead counted above. `src/cost.test.ts` holds the upper bounds so a regression shows up, and `test/load.bench.ts` holds the 100-thread ones.

**What a turn costs the model.** `test/turncost.ts` scripts one turn against the shipped profile with a faux model and measures each request as the provider receives it — role and content, plus a tool result's call id, name and error flag, and a system message whole — so the `details` a UI reads, the usage and the timestamps are not counted. The same turn costs the same bytes on every run: `promptBytes` is every request's system prompt, tool declarations and history, `freshBytes` the part a provider's prompt cache cannot serve from the previous request, and `toolResultBytes` the tool output that entered a prompt. `src/cost.test.ts` bounds all four, plus the request count and the number of system entries in each request.

| Turn (shipped profile, one conversation) | Requests | Prompt bytes | Fresh bytes | Tool declarations | Tool result bytes |
| --- | --- | --- | --- | --- | --- |
| Two-file edit: 2 reads, 2 edits, answer | 4 | 78,541 | 21,558 | 14,454 | 5,402 |
| Question over three files | 2 | 38,791 | 23,465 | 14,454 | 7,599 |
| A call that fails, then the retry | 3 | 49,441 | 18,506 | 14,454 | 2,690 |
| One read, in a conversation that already ran a turn | 2 | 45,494 | 2,760 | 14,454 | 2,534 |

What the numbers say:

- **The loop adds no request of its own.** Every turn makes exactly one request per tool round plus the answer: four for the edit (one read round, two edit rounds, the answer), two for the question, three for the failure and its retry. There is no second request for a system-prompt patch, no re-plan of the tool loadout, and no repeated call after a failed one.
- **The tool declarations are 92% of a conversation's first request** (14,454 of 15,610 bytes, about 3,300 tokens) and every request after it carries them again. They are stable, so a provider caches them, and a turn that follows another adds only its own 2.8 KB; a fresh conversation — every thread — pays them once in full. That block is the whole cost model above storage: 26 tools, of which the schedules' four are 4,246 bytes, the goals' three 1,946, and pi's read, write, edit and `tool_search` 2,810. Cutting it means offering the model fewer tools, which is a product decision, not a loop one.
- **Sections are stable and small.** 726 bytes of section text (`goal-policy` and the schedule authorization), written once as the prompt baseline and patched only when a value changes; the measurement asserts every request of a run carries exactly one system message, so a section that started varying per request would fail the test rather than quietly break every cache.
- **Tool results are the rest of the fresh bytes**, and they are already the smallest form the loop can hold: `edit` tells the model "Successfully replaced 1 block(s)" in 168 bytes and keeps its diff in `details` for the UI, which the provider never sees; a 40-line `read` costs about 2.5 KB and a 50 KB `read` is pi's own ceiling; a failed call costs 157 bytes of diagnostic. A result is re-sent in every later request of the conversation, which is why the prompt-cache share (`freshBytes`) is the number to watch, not the total.
- **`tool_search` was offered with nothing to search.** The MCP row installed it whenever the row was active, including a home with no server connected, where its only answer is "No matching tools found" — 615 bytes in every request and a round trip if the model tried it. It is now installed only while the row has a deferred tool to find (`plugins/mcp/tools.ts`), which takes 616 bytes off every request: the edit turn 81,005 → 78,541, the question 40,023 → 38,791, the retry 51,289 → 49,441, a warm turn 46,726 → 45,494.

**Token spend.** pi keeps `pi.usage` in every conversation: token counts and catalog or provider-reported cost per `provider/model`, plus tool-reported usage per tool, including failed and aborted attempts. `harness.usage()` sums them for the whole Session and `usage.summary` exposes that sum to the Usage pane and the Home spend cell. The ledger has no time dimension, so the models row's own flush turns it into one: `usageRecorder` in `plugins/models/models.ts` reads the live totals, subtracts the totals it last stored (`kv: usage.total`), and adds the difference to `usage_daily` under today's UTC date (migration 4). Each call adds only what the stored total does not already cover, so a replayed or repeated call adds nothing. `usage.summary` flushes first and then answers `spend`/`tokens` (all time) beside `today` and `month` (rows since UTC midnight and since the first of the month). A flush runs at most once a minute, and `usage.summary` flushes on demand, so a day's row is written within a minute of the run that spent it. The timer that flushes only does so when the last flush is a minute old: a full pass reads every conversation's `pi.usage`, and an alarm that wakes for a timer has usually spent nothing. A home that has no watermark yet is seeded at boot with its current totals and books nothing: the counter starts from the first spend it can see, and a ledger that predates this build is never blamed on today. A run that crosses midnight counts in the day it finishes.

**Cap and alerts.** The owner stores a monthly cap (`kv: usage.cap`) and a daily alert (`kv: usage.alert`, default $8) through `usage.cap.set` and `usage.alert.set`. Each flush compares the dated totals with both: a day past the daily alert records `kv: usage.alerted.day` once for that day, and a month past 80% of the cap and past the cap itself records `kv: usage.alerted` once per level. Each new mark pushes one `spend` notification, which the owner can switch off with `notify.set`. The cap is enforced at the door: `message.send` answers `forbidden` while the month's spend is at or above it, so a thread pauses and the owner raises the cap in Usage. Because the ledger moves at most once a minute, the check can lag the newest spend by that minute. A home with no cap set never blocks.

**Per project.** `usage.summary` also returns `byProject`, summed from the `pi.usage` document of each project's coordinator and threads. The root chat belongs to no project, so its spend appears in the totals and in no project row. The ledger itself has no project dimension; this is a sum over the conversations the workspace document names.
